\section{Overview and Background}

NASA \ac{ESDS} manages nearly 180 petabytes of Earth science data today, with
holdings expected to exceed 600 petabytes by the early 2030s. At that scale, a
practical operational problem becomes harder to manage by manual review alone:
metadata records, access guidance, and cloud-optimization artifacts can drift
from the scientific data products they describe. When this happens, users and
automated clients encounter incomplete dataset characterization, stale or
inconsistent \ac{DMR++} inventories, ambiguous units and coordinate conventions,
and brittle subsetting behavior. The result is more failed discovery, more
failed first attempts at access, and more staff time spent diagnosing
collection-specific issues before researchers can begin useful scientific work.

The current ESDS environment already contains many of the pieces needed to
address this problem. \ac{CMR} provides authoritative collection and granule
metadata; Hyrax and \ac{OPeNDAP}/\ac{DAP4} provide remote, subset-oriented
access to the data themselves; \ac{DMR++} inventories expose cloud retrieval
structure; and DAAC and \ac{EDC} teams perform expert review and operational
curation. What remains difficult is applying these capabilities consistently
across large and growing archives, especially when the information needed to
judge a collection is distributed across \ac{CMR} records, service responses,
structural metadata, and the values inside representative granules.

Several approaches already point toward a solution but do not, by themselves,
close the gap. Existing Hyrax directory views and the \ac{CMR} virtual directory
work make collections easier to browse and crawl. Manual metadata review can
identify authoritative corrections, but it does not scale to every collection
and every access pattern. Our proof-of-concept work at the \ac{URI}, summarized
below, showed that an \ac{AI} agent grounded in \ac{OPeNDAP} protocol knowledge
and direct data probes can detect wrong or missing semantic metadata while
distinguishing stated facts from defensible inferences and unsupported guesses.

\ac{AI} is the right tool for this project because the task is not a single
deterministic check; it is an evidence-gathering workflow across many
heterogeneous collections. An agent can traverse collection structure, inspect
\ac{CMR} and \ac{DAP4} metadata, sample representative granules with \ac{PyDAP}
or Xarray, compare findings across granules, draft machine-actionable guidance,
and flag discrepancies for expert review. The factual claims in that workflow
remain grounded in deterministic service responses and programmatic checks of
units, coordinates, ranges, fill values, chunk layout, and cross-granule
consistency.

The proposed work advances the ESDS \ac{AI} Strategy primarily within the
Infrastructure and Access pillars. It strengthens Infrastructure by improving
metadata systems, \ac{AI}-readiness, and open machine-readable interfaces, and
it strengthens Access by making NASA data easier for both humans and \ac{AI}
agents to find and use through existing services. It also supports Governance
and Standards through evidence-linked review of generated guidance and
Operational Intelligence through collection-health signals about metadata and
access readiness. Rather than building a new portal or standalone \ac{AI}
platform, this project modernizes Hyrax and \ac{EDC} workflows so NASA data
remain usable in the external \ac{AI}-assisted environments where researchers
increasingly work.

\subsection{Agentic inferencing}
\label{section-1.1}

Independently of this call, we had already begun probing how well current
foundation models---among them ChatGPT and Claude Code---could reason about
remote data access and the metadata that makes an archive \ac{AI}-ready, using
\ac{OPeNDAP} as our test case. The results were far more striking than we had
anticipated, and when the ESDS call appeared its alignment with that work was
immediate. We summarize that first experiment here; the full write-up, probe
scripts, and evidence-tracked audit reports are available in the open
\texttt{grep-dap} repository~\cite{grepdap}.

The premise was simple. The \ac{OPeNDAP} \ac{DAP} was designed with a rigid
\emph{syntactic} metadata structure (shapes, dimensions, and data types) but a
deliberately unconstrained \emph{semantic} structure (units, coordinates, and
provenance). That design lowered the barrier to publishing data, but it left the
semantic metadata of real archives varying from fully \ac{CF}-compliant to
entirely absent. We asked whether a foundation model, disciplined by the
\ac{OPeNDAP} protocol and by direct statistical probing of the data themselves,
could recover that missing meaning the way an experienced scientist does when
handed an unfamiliar dataset: reading directory and variable names, parsing the
structural metadata, sampling values, and comparing against better-annotated
sibling datasets.

We ran the agent against a live Hyrax server at the \ac{URI}, anchoring every
conclusion in three classes of evidence: catalog-level structure (directory and
file-naming grammar), the structural \ac{DAP4} metadata, and small,
hypothesis-driven hyperslab probes of the data. The results exceeded our
expectations:
\begin{enumerate}[topsep=2pt]
    \item On a \ac{CF}-labelled collection, the agent audited 44 variables and
    flagged two \emph{factually wrong} unit declarations---a wind speed declared
    \texttt{units="mm"} and a pixel count declared \texttt{units="C"}---by
    comparing each declaration against the variable's value range and its
    sibling variables. These are errors a human would have likely caught but,
    well, in this case the human involved missed them.
    \item On an adjacent collection carrying \emph{zero} semantic metadata, the
    agent reconstructed units, coordinate orientation, and variable meaning by
    combining variable-name grammar, inheritance from a better-annotated sibling
    collection, and direct geographic probes. Only one of four candidate
    latitude/longitude conventions classified twelve known land and ocean points
    correctly, fixing the grid orientation unambiguously.
    \item For a derived gradient product, the agent estimated a physically
    essential quantity supplied nowhere in the metadata---the spatial support of
    the differencing operator---at $5 \pm 2$\,km, via three independent methods
    that converged.
\end{enumerate}

Remarkably, after being instructed to learn about \ac{OPeNDAP} and \acs{PyDAP},
the model achieved items 1 and 2 in response to only the following two
straightforward, open-ended prompts:

\begin{enumerate}
    \item Generate a table for https://sst.uri.edu/Aqua/SST\_Orbits/. For each
    variable in the dataset, indicate whether the semantic (COARDS) metadata
    essential for using that variable are complete. If the metadata are
    complete, state that explicitly. If they are incomplete, list the missing
    COARDS metadata and provide your best guess for what the values should be.
    In addition, identify, again for each variable, any semantic metadata that
    are not strictly required by COARDS but that you believe would significantly
    facilitate use and interpretation of the dataset.

    \item Repeat the above for https://sst.uri.edu/gradients\_by\_period/. Since
    this archive has no semantic metadata, you will have to infer whatever you
    can. I suggest that you group the semantic metadata by inferred values for
    which you are very confident, those for which you are not sure but have
    guessed at entries and those for which you do not feel comfortable guessing.
    You should also group these by essential and 'would be nice'.
\end{enumerate}

Critically, the agent distinguished \emph{stated}, \emph{inferred}, and
\emph{not-safely-guessable} attributes; graded each inference by the strength of
its supporting evidence; and explicitly refused to fabricate fields it could not
defend (e.g., \texttt{date\_created}, processing history). This evidence
discipline---inference under explicit confidence, with refusal as a first-class
outcome---is what makes the approach safe to apply to operational archives, and
it directly motivates the curation-plus-risk-management design of the work
proposed below (Sections~\ref{section-2.1}--\ref{section-2.3}).

\section{Proposed Approach}
\textcolor{red}{\textit{Describe your AI-powered solution. What will you build or enhance? What AI tools, models, or frameworks will you use and why? How does this connect to an existing project or operational system? (Suggested: 1–1.5 pages)}}
\textcolor{red}{\textit{Check this since it was rewritten by Codex}}

This project extends Hyrax in the \ac{EDC} with a three-part \ac{AI}-assisted workflow that improves discovery, metadata quality, and autonomous data access without replacing existing operational services. We will use an agentic workflow architecture, implemented with interchangeable large language models and tool-based orchestration such as LangChain where appropriate, to coordinate deterministic calls to \ac{CMR}, Hyrax, \ac{OPeNDAP}/\ac{DAP4}, \ac{PyDAP}, Xarray, and \ac{DMR++} inspection utilities. In this design, the language model is used to guide inspection, compare evidence, and draft collection-level guidance, while factual claims are grounded in direct service responses and programmatic checks of units, coordinates, ranges, fill values, chunk structure, and cross-granule consistency. The three subsections below describe how this architecture first makes collections crawlable by generic \ac{AI} tools, then produces per-collection `usage.md` guidance from validated evidence, and finally embeds approved guidance directly in \ac{DAP4} responses so autonomous clients can retrieve data correctly and efficiently at the point of use.

\subsection{AI-discoverable and crawlable service interfaces}
\label{section-2.1}

In the first part of this project, we propose to use a simple Virtual Directory system that will enable \ac{OPeNDAP} Hyrax in the \ac{ESDIS} to be crawled by commonly used \ac{AI} tools. This project will use a virtual directory subsystem for its own work in part two of this project and end users will use it for part three of the project. Because this will be used by end users, this component must be accessible by their tools. 

We have demonstrated (see Section~\ref{section-1.1} and~\cite{grepdap}) that Hyrax is easily crawled by generic \ac{AI} tools (e.g., OpenAI Codex and Claude Code) when simple directory pages are available. We have also demonstrated that \ac{AI} tools can learn significant details about the underlying data with only that interface and context describing the \ac{OPeNDAP} protocol. Generic \ac{AI} tools are able to discover important information by simply crawling the server and reading extracting data from the files themselves using \ac{OPeNDAP}. This is important because these \ac{AI} tools did this without special interfaces like \acp{MCP} or functions (e.g., using LangChain) and thus, more closely mirror what end users will likely have at their disposal.

We have two Virtual Directory systems that the project can use: one developed by \ac{OPeNDAP} that follows exactly the interface used by other \ac{OPeNDAP} servers and one developed by the \ac{CMR} team~\cite{cmrvdi}. We will use the one that is the most expedient, based on the project's needs and \ac{ESDIS} guidance. The main advantages of the interface developed by \ac{OPeNDAP} is that we know it will work seamlessly with common \ac{AI} tools and using it will ease re-use of this work by other groups running \ac{OPeNDAP} servers.

\subsection{AI-assisted metadata introspection and validation}
\label{section-2.2}
In part two of the project, we propose to deploy an Agentic \ac{AI} to crawl and identify all collections that are enabled by \ac{OPeNDAP} in \ac{ESDIS}. The output of this component will be one Markdown file per-collection produced by the agentic \ac{AI} (see Figure~\ref{fig1:placeholder}). Each of these files will contain usage metadata common to all granules in the collection, based on both \ac{CMR} metadata and data and metadata extracted from direct access to the granules made using the \ac{OPeNDAP} service. Each metadata file will be stored in a separate bucket from the collection to mitigate issues with \ac{DAAC} data bucket ownership.

\begin{figure}
    \centering
    \includegraphics[width=.75\linewidth]{Figure3.png}
    \caption{How agentic \ac{AI} builds usage.md documents for NASA \ac{ESDIS} collections.}
    \label{fig1:placeholder}
\end{figure}

As soon as these metadata documents are written, they can be analyzed to see if they disagree with any of the information in \ac{CMR}. In this way, part two of the project accomplishes two goals. It provides a way to perform curation on legacy collections that have already undergone ingest, and it, for any discrepancies found, can bring in a data expert to determine how to address the differences. Thus, our project combines curation and management of the risk that the agentic \ac{AI} tool `hallucinates' and the result in unwittingly used.

Because we have access to information in the \ac{DMR++} through the \ac{OPeNDAP} interface, the metadata documents this \ac{AI} tool builds can also include information about optimal retrieval strategies based on the sizes and locations of `chunks' within the granule. We can also use the \ac{AI} tool to investigate chunk sizing and compression consistency of the granules in a collection. The tool can check for problems that may be specific to a given data set and offer ways to compensate for those problems. This metadata is accessible for such a wide range of collections nowhere else in the \ac{ESDIS} system. This could be used by virtual data systems like {\em VirtualiZarr} to improve their operation.

When inconsistent or missing information is identified in the generated metadata documents, the expert can use \ac{AI}-driven workflows with tools such as \ac{PyDAP} and Xarray to intelligently sample datasets and validate metadata characteristics {\em directly from the underlying scientific data} using \ac{OPeNDAP}. With its data-proximate subsetting, \ac{OPeNDAP} is an ideal tool to probe the contents of the data and identify relationships between the data and metadata such as units, scale factors, fill values, coordinates, dimensions, and value ranges.

\subsection{Machine-actionable guidance for autonomous data retrieval workflows}
\label{section-2.3}

% The final component of the project will exploit the markdown files described in the previous part. Since each per-collection markdown file will describe sets of skills and executable instructions that Agentic AIs will rely on as workflow guidance, retrieval recipes, and machine-readable operational context, we propose to embed such markdown files into Hyrax \ac{DAP4} responses in ESDIS. These enhancements will enable autonomous agents, which we expect users will increasingly become more reliant upon, to effectively utilize NASA Earthdata resources while reducing retrieval inefficiencies and failed access patterns.

While Parts 1 and 2 make collections discoverable and queryable by \ac{AI} tools, the value of the curated guidance is only fully realized if agents receive it at the point of retrieval. Part 3 therefore embeds the collected metadata in the data and metadata responses of the \ac{OPeNDAP} service. The {\em usage.md} file becomes a payload for the \ac{DAP4} responses. These verified, evidence-tagged facts are written to a per-collection `usage.md` and embedded in the collection's \ac{DAP4} responses. A downstream autonomous agent then consumes it in-band, at the moment of retrieval, and issues a correct, chunk-aligned subsetting request on the first attempt—without a separate discovery round-trip and without guessing at units, coordinate orientation, or fill conventions. This is the difference Part 3 delivers: the curated guidance from Part 2 travels with the data, turning queries that agents already make into queries that succeed.

We have already exercised this workflow end-to-end against a live Hyrax server running at the \ac{URI} (proof-of-concept). The example in Listing~\ref{listing-1} recasts that for the \ac{EDC}, where collections already carry detailed \ac{CMR} and \ac{CF} metadata and the agent's job is primarily verification and cross-granule accumulation.

\begin{lstlisting}[caption={Proof-of-concept example run against Hyrax at the University of Rhode Island and recast for the NASA EDC}, label={listing-1}]
> **Worked example: from per-granule verification to a retrieval recipe**
>
> - **Value-range vs. declared units.** A small DAP4 hyperslab request confirms that a variable declared `units="kelvin"` actually spans ~270-310, not ~-3-35. In the proof-of-concept this same check caught two genuinely mislabeled variables (a wind speed declared `"mm"`, a pixel count declared `""``).
> - **Cross-granule accumulation.** Per-granule spatial/temporal bounds, fill-value usage, and valid ranges are aggregated into a single collection-level envelope, and divergence between granules is flagged.
> - **Cross-checks against CMR.** Accumulated bounds are compared with the collection's CMR record; disagreements are surfaced for an expert rather than silently overwritten.
> - **Retrieval-relevant structure.** DMR++ chunk sizes and layout are read directly, yielding concrete subsetting guidance (chunk-aligned request shapes, byte ranges, and dataset-specific pitfalls).
\end{lstlisting}

\textbf{What the agent does, per collection} Walking the granules of a collection through \ac{OPeNDAP}, the agent (1) confirms that the stated semantic metadata is internally consistent across granules and consistent with the data itself, and (2) accumulates collection-level facts that no single granule record exposes. Each finding is anchored in evidence and graded by confidence, and the agent explicitly refuses to assert anything it cannot defend.

\section{Limitations and Challenges}
\textcolor{red}{\textit{Be honest about what could go wrong, what is uncertain, and what dependencies exist. How will you manage or mitigate these? (Suggested: 0.5 pages)}}

Each of the three parts of this project have risks. The deployment of our existing Virtual Directory Interface has been hampered by a different interface with overlapping functionality developed by the \ac{CMR} team. If \ac{ESDIS} does not approve the deployment of our interface, we will need to reassess if the Hyrax service in the \ac{EDC} can be crawled by generic \ac{AI} tools. Secondly, We propose to develop an agentic \ac{AI} tool to build the metadata documents in part two. This will be a significant undertaking using technology that is very new and rapidly changing. Our group will need to adapt traditional software engineering to a new kind of system, particularly for this second phase because we foresee developing tools/functions using LangChain and/or LangGraph. We will need to develop automated tests and \ac{CICD} for the products of those development efforts. Lastly, in the final part of the project, documents representing the contents of NASA data sets will be accessible to end-users. The workflow for this part of the project includes a review of the documents by an expert, but the potential for misrepresenting data still exists.

We understand that this project will have greater risk, and different kinds of risk, than the software development done for our NASA subcontract. To address those `unknown unknowns,' we will take advantage of the cohort of teams also funded by this call to seek advice and share solutions to problems. 

\section{Deliverables}
\textcolor{red}{\textit{List the specific outputs you will produce: working prototype, integration, documentation, code repository. Be concrete. What will exist at the end of the project that does not exist today? (Suggested: 0.5 pages)}}

We will produce three deliverables:
\begin{enumerate}
    \item A Virtual Directory Interface that enables crawling \ac{OPeNDAP}-enabled data sets in \ac{ESDIS} using generic \ac{AI} tools. This will follow the existing interface provided by Hyrax and other \ac{OPeNDAP} servers. This will use an existing prototype that has already run in the \ac{EDC} system. This will be integrated into the Hyrax software deployed in \ac{ESDIS}. This web-friendly user interface is already well documented. The software is already in an open GitHub repository managed by \ac{OPeNDAP} (as is all the Hyrax software).

    \item An agentic \ac{AI} tool that can crawl \ac{OPeNDAP}-enabled data in \ac{ESDIS} and build comprehensive metadata documents written in markdown format. Using markdown streamlines use of the documents by generic \ac{AI} tools. This tool will be used internally to build and maintain these documents. The use of this software and its design will be documented. The software will be hosted on GitHub in a public repository maintained by \ac{OPeNDAP}.

    \item A collection of comprehensive metadata documents that users can access using the \ac{OPeNDAP} service in \ac{ESDIS}. This will be open to the public. We will provide documentation for end-users that will guide them through common use cases. This documentation will be written in Markdown or AsciiDoc and provide just as we have provided documentation on Hyrax and \ac{DMR++} in the past. In addition, we will provide tutorials with code for end-users, similar to the other tutorials we have written for NASA data
\end{enumerate}

\section{Validations and Path to Operations}
\textcolor{red}{\textit{How will you know it works? Who will test or validate the output? What would need to happen for this to move from prototype to operational use? (Suggested: 0.5 pages)}}

\textcolor{red}{\textit{Check this since it was rewritten by Codex}}

Our validation approach follows from the three deliverables. For Part 1, we will validate the Virtual Directory Interface by confirming that generic \ac{AI} clients can discover and traverse representative \ac{OPeNDAP}-enabled collections in \ac{ESDIS} without collection-specific adaptation. Success will be measured by whether the interface exposes the expected collection structure and whether autonomous crawlers can reach the same collection endpoints that expert users reach.

For Part 2, we will validate the agentic metadata-generation workflow by comparing the generated markdown documents against authoritative sources, including \ac{CMR} collection and granule metadata, and the results of direct \ac{DAP4} inspection. The system will be judged on whether it produces complete, evidence-linked metadata summaries, correctly flags uncertainty or disagreement, and avoids asserting facts that are not supported by the data or upstream metadata. Members of the project team, together with collaborators familiar with the selected \ac{ESDIS} collections, will review a representative sample of these generated documents to confirm that they are accurate and useful for downstream retrieval tasks.

For Part 3, we will validate operational usefulness by testing whether an autonomous client can use the embedded guidance to make correct data access and subsetting requests on the first attempt more often than a baseline workflow that relies only on conventional metadata records. We will evaluate whether the resulting requests are retrieval-correct, reduce avoidable iteration, and capture dataset-specific constraints that are often learned today only through expert experience.

The path to operations is intentionally incremental because this project extends existing \ac{OPeNDAP} and Hyrax capabilities rather than introducing a new service that must be adopted independently. The Virtual Directory Interface can be incorporated into Hyrax deployments using the same software distribution mechanisms already used for \ac{OPeNDAP} server updates. The metadata-generation software will be maintained in an open repository so that it can be inspected by NASA partners, and improved through operational experience. The generated markdown guidance can be reviewed by domain experts before publication and then served through existing \ac{DAP4} responses, allowing adoption first in pilot collections and then, if successful, across additional \ac{ESDIS} holdings.
